# SVA IEEE corpus contract (steps 1 and 2)

`sva-ieee-corpus/` (repository root) is a corpus for **other tools**: one small native-SVA case per hand-written trace case, with the expected result taken from the trace table. It is generated by `tests/support/trace_suite.py` and committed. These tests enforce the guarantees below. No external tool is needed or run; the corpus has no tool-specific configuration (SBY, EBMC or simulator options are the consumer's business).

## Source and ownership

1. **The trace tables are canonical.** Every expectation comes from `tests/functional_tests/reference_semantics/fixtures/*.trace`; none is computed from sva2yosys or from any tool's output. The corpus quotes no IEEE text: only clause numbers (from the tables) and the property text of the cases.
2. **Generated, never edited.** Every generated SV file starts with a header comment saying so and naming the generator (CSV and JSON have no comment syntax: `manifest.json` names the generator and the folder README says the files are generated); files are UTF-8 with LF line ends; output is sorted and deterministic (two runs are byte-identical).
3. **Case id** is `<trace file stem>/<case name>`. Case names are unique within a trace file, so ids are unique.

## What is exported

4. **Exported: every case of the tables** (661 cases, all `support: oracle` cases included: our tool rejects them, the annotation is kept in the manifest, and the case is still valid SVA for other tools). Every case appears in the manifest exactly once, with `exported: true`.
5. **Categories.** Each case belongs to exactly one category, by this priority: `initial` (`procedure: initial`), `cover` (`kind: cover`), `assume` (`kind: assume`), `live` (has a `loop`: an infinite repeating trace), else `bounded` (a finite assertion). The folder under each root is the category.
5a. **Files per case.** A case has `formal/`, `traces/csv/` and `traces/wavedrom/` files, and a `sim/` file unless it is a *lasso* (point 30).

## Files

6. **Layout:** `sva-ieee-corpus/manifest.json`; `README.md` and `LICENSE` (MIT; hand-written, not generated); and per exported case four files with the same `<category>/<trace file stem>/<case>` path under four roots: `sim/<path>.sv`, `formal/<path>.sv`, `traces/csv/<path>.csv`, `traces/wavedrom/<path>.json`. There is no shared file: **every example is self-contained.**
7. **Both SV forms declare module `sva_case`** with input `clk`. Its signals are driven internally from the trace (*Stimulus*); it has no other input.
8. **Formal form:** the driver and the property only: no clock generator, no `$display`, no `done`, no assumptions. The directive is `p: <kind> property (@(posedge clk) [disable iff (d)] <property>);` with `<kind>` the table's `assert`, `assume` or `cover` and the property text exactly as in the table; for `procedure: initial` it is written `initial p: ...` (point 28).
9. **Simulation form:** the same module plus an output `done` that rises after the last written sample, the same assertion `p` with action blocks that `$display` a line per failure and per success (one assertion only: a plain failing assertion would stop some simulators), in the fixed format `SVA_FAIL <case id> sample=<k>` and `SVA_PASS <case id> sample=<k>` (`<k>` the sample index, printed as `$sampled(tick)`, IEEE 1800-2017 16.9.3: the Preponed value of the counter, i.e. the number of the sample the assertion evaluated, whatever the order in which a simulator runs the counter update and the action block). The pass action also fires on vacuous success unless the simulator is told `$assertvacuousoff` (IEEE 1800-2017 20.12), so for a case with `scope: attempt` the `SVA_PASS` lines are a superset of the manifest's non-vacuous `successes` (for the other scopes `successes` may be obligation-level observations that an action block does not report: point 17 and the README), and, in the same file, a top module `tb` that generates the clock and ends the run when `done` is high. Compiling the one file with `tb` as top is all a simulator needs.
10. **CSV:** header `sample,<signals...>,fail,pass`; one row per written sample; signal values as unsigned decimal, `fail` and `pass` as 0/1 (the table's expected rows). LF line ends.
11. **WaveDrom:** valid WaveDrom `signal` JSON of the same data: `clk`, each signal (1-bit as `0`/`1` waves that write a value only where it changes and `.` otherwise, because WaveDrom draws a repeated explicit value as a spike; wide signals as `=` data waves labelled in hex, one box per run of equal values), the textbook drawing: the cell of sample `k` ends at the rising edge `k` that samples it (values change at an edge), so the clock is a low cell followed by one rising edge per cell, `lp..` for four samples, and the last edge, which closes the last cell, is not drawn; no lane has a `phase`; the header `tock` labels in the middle of the cells are the sample numbers (the first low cell is a full cell, although the testbench's first low period is half a period); a signal read only by the `disable iff` condition is drawn one cell later (cell `k` shows row `k - 1`, row 0 in cells 0 and 1), because the condition reads it right after the edge, and a `foot` line names such signals and the expected `fail` and `pass` rows. It is for reading; no tool consumes it.

## Stimulus (inside each SV file)

12. **A string per signal** repeats the table's row and is decoded by plain bit selects on the sample counter (no `string` type, no file). Fields are separated by one space, so the stride is `digits + 1`. **1-bit rows** use `.` for 0 and `1` for 1. **Wide rows** use `ceil(width/4)` uppercase hexadecimal digits per sample, zero written `0` in every digit (`0x00` is `00`, `0x10` is `10`); a wide row never contains `.`. The decoder also accepts `.` as a zero digit, but the generator writes only this canonical form, and a test checks it. A comment above the strings repeats the rows in the layout of the `.trace` file. This is the form of every case of fewer than 30 samples; the cases of 30 samples or more are written in the ternary form (point 25).

## Driver semantics

13. **Samples.** Sample `k` is the value sampled at the `k`-th `posedge clk`, counting from 0; the first `posedge clk` samples sample 0. Values change only after the sampling edge. The counter, width rule, hold-last rule and directive line are those of `tests/support/trace_driver.py`, which the EBMC differential design shares. **A `disable iff` condition reads current values** (IEEE 1800-2017 16.12), after the non-blocking updates of the time slot, where a driver that moved to row `k + 1` at the rising edge would show it row `k + 1`; so a signal that only the condition reads (`disable_only_signals`: never one the property reads, the generator refuses such a case, and none exists) is selected by a saved copy of the counter, `tick_prev` (`phase_prev` for a lasso), which holds the counter before the last edge and so shows row `k` after edge `k`. Everything stays on `posedge clk`.
14. **Finite boundary.** Only samples `0 .. N-1` (N = the written sample count) have expectations. The last values are held afterwards only so that the design stays defined; a consumer must bound its check to `N` samples, and a result after sample `N-1` is not part of the expectation. A pending attempt at the end is not an online failure (no failure is reported for it at a sample); what finalizes false when the simulation ends is `final_fail` in `attempts` (point 31).
15. **Signals** are the table's declared signals, with their widths; `clk`, `t`, `success`, `p` are reserved as in the tables. All values are two-state.

## Manifest

16. **Fields per case:** `id`, `category`, `kind`, `scope` (`default` | `first-failure` | `attempt`), `samples`, `failures` (sample indices of the table's `fail` row), `successes` (of the `pass` row), `class` (`normative` | `implementation-defined` | `interpretation`), `interpretations` (the `I<n>` rows), `clauses`, `support_oracle`, and `exported`. The top level has `traces-sha256` (the digest of the trace files, as in `ebmc_differential.traces_digest`), the case count and the exported count.
17. **Meaning of `failures`:** the samples at which the assertion reports a failure on a sample-indexed run. With `scope: first-failure` it is the first failure alone (the other failures are not specified). With `scope: attempt` it is the decision sample of every false attempt. A consumer compares the set of sample indices; failure *timing* beyond that, nonvacuity and per-attempt results are step 2.
18. **Evidence class is visible.** An `interpretation` case depends on a reading of the standard (the `I<n>` rows of the interpretation list); a consumer decides how to treat it. The manifest never marks a result as "agreed by a tool".

## Freshness (default tier, no external tool)

19. `check_corpus` regenerates in memory and compares with the committed files: it reports a **changed** file, a **missing** file, an **extra** generated file, and a stale manifest (including a changed `traces-sha256`). The test fails on any difference, with the instruction to run `uv run python tests/support/trace_suite.py --write`. Adding, removing, renaming or editing a trace case, or changing the generator or the shared driver, is therefore caught.
20. `write_corpus` removes generated files that are no longer built, and never touches `README.md`, `LICENSE` or any other file. Only paths of the form `manifest.json` or `<sim|formal|traces/csv|traces/wavedrom>/<category>/<stem>/<file>` with extension `.sv`, `.csv` or `.json` are generated files (for the check, the removal and the empty-folder cleanup alike): notes, repository metadata and other folders in the destination survive, and the freshness check does not look at them.

## Own validation

21. **Elaboration.** A spread sample of the exported SV files parses and elaborates under Slang in the default tier, and every exported file does in the extended tier (point 33). A control with a malformed property fails.
22. **Round trip (representative).** A fixed sample of exported cases (about 20, spread over scopes, widths and sampled-value functions; cases with `disable iff` are left out because sva2yosys rejects `disable iff` on signals the corpus drives from its counter, the deferred internal-signal case) is lowered by sva2yosys from the exported formal file, executed, and its failure samples compared with the manifest. It uses the existing local flow; with tools unselected it is skipped. It is not a replacement for the direct trace tests, which stay.
23. **Driver sharing and decoding.** `ebmc_differential.design_source` and the corpus use `trace_driver` (counter, phase, directive); the EBMC design keeps its calibrated conditional-chain stimulus, and a test checks that its text for every case and engine is byte-identical to the pre-extraction text (fixture of digests). A test decodes every stimulus string of the corpus and compares it with the table's samples, and checks that each string is the canonical form (point 12).
24. **Tool reading (evidence).** The string stimulus was read correctly by Slang, Verilator 5.047 and EBMC 6.1, and its decoding by the Yosys slang plugin; the plugin itself rejects concurrent assertions, which is outside this contract.

25. **Ternary form and the threshold.** The trace can be written as a chain of conditional expressions on the sample counter (the style of the EBMC differential design) instead of the string rows. Two options write it: `trace_suite.py --write --stimulus ternary --root <dir>` writes every case in it, for a tool that cannot read the string rows (same files, same manifest apart from `"stimulus": "ternary"`); `--ternary-from N` (a positive integer, or `never`) writes the cases of `N` samples or more in it and the others as `--stimulus` says. **The committed corpus uses the threshold 30** (`TERNARY_FROM`): its two cases of 30 samples or more (`ieee_16_7_req_range_4_to_32_latest` and `..._too_early_and_too_late`, 33 and 34 samples; the next longest has 14) are ternary in both forms, in the formal and the simulation file, and every other case is the string form. The manifest says `"stimulus": "string"` and `"ternary-from": 30` (`null` when the option is `never`). The reason is a measured limit of the Yosys flow, not of the standard: a trace of 30 samples or more in the string form is a constant of 500 bits or more read with a variable index, which `read_verilog` turns into a netlist whose SMT form nests about a thousand `concat` terms, so that SBY's own engine (`yosys-smtbmc`) stops with `RecursionError` whatever the property; the ternary form of the same cases checks correctly. A corpus that our own flow cannot check would not be shipped. Any other value, and `--stimulus ternary`, are on demand: they need `--write` and another `--root` (the committed corpus is written with the committed values only, and the freshness check applies to them). A sample of ternary files elaborates under Slang in the default tier.

26. **Sample-index option.** `trace_suite.py --write --sample-index register --root <dir>` prints the sample number from a register `sample_idx` that copies the counter at each falling edge instead of `$sampled(tick)`, for a simulator that lacks `$sampled` in action blocks (the manifest says `"sample-index": "register"`). Like the ternary option it is on demand: the committed corpus is the default form, writing it in an alternative form or checking an alternative tree is refused. The options combine.

## Step 2: the other categories

27. **`cover`.** The pass statement of a cover is the observation: `successes` (the table's `pass` row) are the samples at which the property succeeds non-vacuously, and `failures` is empty (a cover has no failure). The simulation form is `p: cover property (...) $display("SVA_COVER <case id> sample=<k>");`, printed once per successful evaluation attempt: the pass statement also runs on vacuous successes (IEEE 1800-2017 16.14.3, 20.12), so the lines are a superset of `successes` unless the simulator disables the vacuous pass action. A formal tool that does not count a vacuous success should find the cover reachable exactly at the `successes` (within the written samples).
28. **`initial`.** A directive in an `initial` procedure has one attempt, at the first tick (IEEE 1800-2017 16.14.6). Both forms write `initial p: <kind> property (...)`, the simulation form with the action blocks of its kind. The expectations are those of the table (they concern sample 0).
29. **`assume`.** In the simulation form an assumption is written `p: assume property (...)` with the same action blocks as an assertion; a violation is reported as `SVA_FAIL`. In the formal form the assumption constrains the run: if the replay violates it (the manifest `failures` are not empty), the run is infeasible from the first violation on, which a formal tool must not report as a proof; the manifest records the violation samples and nothing else about the formal result.
30. **Lasso cases** (`loop` = L is set; 94 cases in `live`, `assume` and `cover`). The trace is infinite: samples `0 .. N-1`, then `L .. N-1` repeating forever. The driver has no counter and no `done`: a counter `phase` runs `0 .. N-1` and jumps back to `L` (`trace_driver.phase_lines`), and the stimulus is selected by `phase`. A lasso case has no simulation form (a simulation runs a prefix only, and the infinite outcome of a strong operator needs the infinite trace); the manifest says `"sim": false` and the other files exist. The `failures`, `successes`, `pending` and `final_fail` of a lasso case keep the table's meaning: the written samples read as a finite trace. The infinite expectation is in the `infinite` object (point 31).
31. **Manifest additions.** Every entry has `loop` (L or null) and `sim` (bool). A lasso entry has `infinite`: `outcomes` (a string, one of `T` true, `F` false, `D` disabled for the attempt started at each written sample, on the infinite trace) and `decided` (per start sample, the sample at which the attempt is decided online, or null when no finite prefix decides it). An entry whose table has per-attempt results or end-of-simulation results (`pending`, `final-fail`) has `attempts`: `outcomes` (one of `T t F f U X p d` per start sample: true non-vacuous, true vacuous, false non-vacuous, false vacuous, true or false with non-vacuity unknown at the end, pending, disabled), `decided`, and, when the table gives them, `pending` and `final_fail` (counts of attempts pending at the end and of pending attempts that finalize false). Keys absent from the table are null. A directive in an `initial` procedure has one native attempt, so its `outcomes` and `decided` keep the first entry only (the later start positions of the table are bookkeeping of the lowered form). `successes` has the meaning of the table's `pass` row: for `scope: attempt` the successes of whole evaluation attempts, for the other scopes possibly obligation-level observations that a native action block does not report (the README says so).
32. **CSV and WaveDrom of a lasso case** have two more rows or columns: `repeat` (1 from sample L on) and `outcome` (the infinite outcome T, F or D of the attempt started at that sample). Other cases keep the point 10 and 11 format.

## Step 2 validation

33. **Every exported SV file** (all categories; the simulation form where it exists) elaborates under Slang: a sample covering every category, every kind, a lasso and an `initial` in the default tier, every file in the extended tier.
34. **Round trip.** A default-tier sample of formal files per category (not `support: oracle`, no `disable iff`) is accepted by sva2yosys; a sample of finite covers lowered and run in SBY cover mode reaches the cover exactly when `successes` is not empty (opt-in tier).
35. **Counts.** The manifest counts are the independent counts of the tables: 661 cases, `bounded` 490, `cover` 62, `assume` 19, `initial` 11, `live` 79 at this revision (the test derives them from the tables, not from these numbers), `sim: false` exactly for the cases with a `loop`.

36. **Timing is documented.** The corpus `README.md` has a section *Timing conventions*: the two reading rules of IEEE 1800-2017 (sampled values, 16.5.1 and 4.4.2.1; current values for a `disable iff` condition, 16.12), why a signal read only by the condition is presented from a saved counter, the meaning of sample `k`, the timeline of the testbench and driver (first rising edge at time 5, the counter updated after each edge), the meaning of a CSV row and how to drive a design from it, the WaveDrom drawing, and one case in the three views. It paraphrases the standard and cites clauses; it quotes no text of it. A test checks that the section and these elements are present.

37. **The `disable iff` signals.** In every exported SV file the signals of `disable_only_signals` are decoded with the saved counter and no other signal is; a file of a case without `disable iff` has no saved counter; all 68 `disable iff` cases of the tables build (no signal is read by both). The timing is checked by simulation, with hand-written expectations (opt-in, `--external-tools=verilator`, extended tier, `test_driver_timing.py`): the formal form of a finite case with a wide `disable iff` signal and of a lasso, its assertion removed, is simulated and the value of every signal is printed at each rising edge before the non-blocking updates (what a property samples: row `k`, then row `k + 1` after the edge) and after them (what the condition reads: row `k`), over the first and last samples, the hold of the last row and the lasso wrap; a control without the saved counter must show the condition row `k + 1`. It is also checked structurally by the tests of the driver and of the generated text.

38. **The whole corpus through sva2yosys** (found by running it: `go |-> a[*0] ##0 b` made the rewrite crash with a `KeyError`). Two tests, beside the samples of point 34:
    - **Generation, every case** (`extended`, no tool). `sva2yosys formal.sv --top sva_case -o DIR` never raises, for each of the 661 cases. It exits 0 exactly for the cases our tool takes and 1 for the others, which are exactly the `support: oracle` cases (19) and the cases with a `disable iff` that reads a signal (the signals of the condition are the saved counter, which is not a top-level input, point 37; 67 cases; `disable iff (1'b0)` reads none and is taken). A crash, or a case outside these two groups that is rejected, fails the test.
    - **SBY verdict, every taken case** (`slow`, needs SBY). Every case that point-38 generation accepts, except the `assume` cases (a design with only an assumption has no assertion: SBY reports an error, `yosys_contract` point 12) and the two cases of the engine limit below, is checked with SBY (`bmc` to depth `samples` for an assert or an `initial` assertion, `cover` for a cover) and gives the verdict of the table: failing exactly when the table has failures, at the earliest failing sample; a cover reached exactly when the table has successes. Lasso cases are checked as finite prefixes (their liveness part is not read, `sva2yosys_read.ys`).
    - **Engine limit, caused by the stimulus driver (string form).** `ieee_16_7_req_range_4_to_32_latest` and `ieee_16_7_req_range_4_to_32_too_early_and_too_late` (`go |-> req ##[4:32] gnt`, 33 and 34 samples; the next longest case has 14) make SBY's own engine (`yosys-smtbmc`, `smtio.py` `unroll_stmt`) stop with `RecursionError`. The monitors are not the cause: the same driver with a trivial property (`go |-> go`) stops the same way, while `go |-> req ##[4:N] gnt` with a free `req` checks for every `N` up to 48; and `read_slang` (`--yosys-frontend slang`) checks both cases. What the two have is a 520-bit stimulus string per signal, decoded with a variable part-select, which `read_verilog` turns into a netlist that this engine cannot unroll. Measured: the ternary form of the same two cases checks correctly under `read_verilog` (PASS, and FAIL at sample 32, as the table says). The committed corpus therefore writes these two cases in the ternary form (point 25), and the test checks the committed files as they are.

39. **Another solver on the round-trip sample** (`extended`, needs SBY). The sample of point 34 is checked again with `smtbmc z3` instead of `smtbmc yices`: the same verdicts and the same earliest failing sample as the table. A verdict that depends on the solver would show here.

## Out of scope

Tool adapters and verdicts of any tool, golden waveforms, and a liveness-engine configuration; simulation of infinite traces.
